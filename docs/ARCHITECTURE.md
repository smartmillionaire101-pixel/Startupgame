# Architecture

## Principles carried from the design document

| Design principle | How the code honours it |
| --- | --- |
| Real data sets conditions; simulation decides outcomes | `engine/src/data/*` holds sourced market snapshots; live feeds only issue `market.data` commands. No outcome reads a feed directly. |
| Systems connect | Lifestyle → hours/energy → product output → customers → revenue → valuation → fundraising → exits → savings → lifestyle. All one engine, one settlement. |
| The world persists | Append-only command log + snapshots; exact replay on boot. |
| Short and sharp | Read models (`views.ts`) pre-compute what each screen needs; articles ≤ 60 words, alerts ≤ 12 (tested). |
| Honesty is checked | Pitch answers and press claims are checked against game data (`fundraising.ts`, `media.ts`). |
| Failure is part of a career | Shutdown waterfall, reputation by how you fail, comebacks, the floor. |
| Money can't buy success | No payment code exists; monetisation is deferred (§19). |

## Engine (`packages/engine`)

- **Pure and deterministic.** All randomness comes from `rng.ts`, derived per purpose from the world seed (`deriveRng(seed, 'settle', market, month)`), so adding a random draw in one system never shifts another. `Math.random` is banned by lint.
- **Commands in, world out.** `dispatch(world, command, { actorId, now })` validates rules and returns a new world (Immer). A rule violation throws `GameRuleError` and the *whole* command rolls back — no half-executed deals.
- **Double-entry money.** Every movement is a ledger transfer between accounts in one currency; the outside world (AI customers, tax authority, LPs, FX desks) is modelled as external accounts. The sum of all balances per currency is always zero — a property test checks it against random play.
- **Integer money.** Minor units only (kobo, cents, pence). Floats never touch balances.
- **Privacy by projection.** The world holds everything; `playerView` returns only what that player may see. AI negotiation limits and the truth behind pitch options are stripped (tested).

Key modules: `customers.ts` (segments capped by real buyers, funnel, competition), `staff.ts` (talent pool, negotiation, morale), `captable.ts` (SAFEs, priced rounds, pool shuffle, waterfall), `fundraising.ts`, `deals.ts` (deal cards), `media.ts` (outreach, fact-check), `company.ts` (monthly operations), `personal.ts` (lifestyle, hours, gigs, FX), `funds.ts` (Fund I, fees, carry), `ai.ts` (AI population), `settlement.ts` (the month). Phase 2: `credit.ts`, `travel.ts`, `marketplace.ts`, `governance.ts`, `acquisitions.ts`, `arbitration.ts`, `banks.ts`, and `upgrade.ts` (schema upgrades for saved worlds). Wave 1: `story.ts` (the monthly story: why the month went the way it did, ranked by impact, with suggested next moves) and `rescue.ts` (distress levels, the rescue plan and its moves: cut costs, hibernate, bridge SAFE, fire sale), and `capital.ts` (per-market AI lenders and products from `data/capital.ts`, eligibility with plain-language reasons, depth-scaled funds). Wave 2: `events.ts` with `data/events.ts` (player-hosted city events: `event.host` / `event.rsvp` / `event.cancel` move money host → market suppliers and ticket attendee → host, refunds on un-RSVP and cancel; events are held at the settlement closing their month, after customers and before companies, on their own RNG stream `deriveRng(seed, 'event', id)`; AI turnout from kind, budget, host stars, capacity and `vcDepth` for investor events; outcomes are `player.contacts` (warmth fading over 12 months), customer leads, referred candidates (`Candidate.referredFor`, keener in `evaluateOffer`), network, trust and a host star nudge). Warm intros live in `fundraising.ts`: a warm fund contact relaxes `minStars` by up to one star and adds to the first-meeting score (`firstMeetingScore`), and network above 30 adds a little. `world.events` and `player.contacts` are optional, so saved worlds need no schema step.

Wave 3 (section A): **San Francisco** (`'san-francisco'`, `data/markets-wave3.ts`, opened by `market.open` from the `WAVE3` list) is the first dollar market. Its local account *is* a USD account: `fxRate` treats USD as 1, `convert` between two accounts in the same currency is a plain transfer (no desk, no fee), dollar conversions anywhere go through the single world USD desk (`world.usdExt.fx`), `market.data` never moves its `unitsPerUsd` off 1, and an SF player can't open a second dollar account (`usd.local`). Its fiction lives with Phase 2's in `data/fiction-phase2.ts`; lenders, QSBS/SBA 7(a) schemes and depth (vcDepth 1.6, angelDepth 1.8) in `data/capital.ts`. **AI angels** (`angels.ts`): each market keeps `max(2, round(4 × angelDepth))` AI players with role `investor`, each running a small angel fund made by `createAiFund` (`fund.angelId` → the angel, `player.angel.fundId` → the fund, `managerId` stays null because it means "a human runs this fund"). Ids are stable (`ai_angel_<market>_<n>`, `fund_<market>_angel_<n>`) and every draw uses the `'angels'` RNG label, so their arrival never shifts other ids or draws; `aiFundsInvest` skips angel funds for the same reason. Monthly, after the AI funds, each angel backs at most one company with a SAFE: AI companies that are raising or young take it straight away; human founders who are raising or pitched in the last three months get a SAFE deal card. `ensureAngels` (from `openMarket` and `maintainPopulation`) retires angels whose fund can't write its smallest cheque, replaces them, and gives saved worlds their angels at the next settlement (no schema step). Views: `view.players` includes active AI angels (`ai: true`, `angel: { fundId, fundName, sectors, check }`; humans have `ai: false, angel: null`), and `view.market.funds[].angel` is `{ playerId, name }` for angel funds, `null` otherwise.

Wave 3 (section B): **the city economy**, `economy.ts` with `data/businesses.ts` (business kinds: category, venue items, takings, `buys` shares per startup sector, gigs, look; and a 24–36 business roster per city with district ids shared with the web's city plans). `m.businesses` (optional; `ensureBusinesses` seeds it at `market.open` and, for saved worlds, at the next settlement; ids and account ids are deterministic `biz-<market>-<n>` / `acc:biz-…`, so no other id shifts) holds `LocalBusiness`es, each with a real ledger account funded from `ext.genesis`. `settleEconomy` runs in `settleMarket` after segments and events and before companies, on `deriveRng(seed, 'economy', market, month)`: households pay takings (`ext.customers` → business), wages go to `ext.payroll` and rent and stock to `ext.suppliers`, each `buys` sector's share of takings goes to the business's startup supplier (`transferUpTo` → company, booked in `ledgerThisMonth.businessRevenue` and so in `MonthlyPnl.revenue`/`businessRevenue`) or to the incumbent (`ext.suppliers`); AI startups win and switch accounts by `supplierScore` (price vs budget, reliability, fit, stars, awareness, owner rapport, with inertia), poor reliability/price/hibernation loses them; health follows profit, closures return cash to `ext.genesis`, the owner draws surplus to `ext.lifestyle`, and roster places open over time. Wins and losses reach the monthly story via `company.businessNews`. Commands: `business.pitch` (6h, 4/month, deterministic yes / come back later with a specific reason / no, `deriveRng(seed, 'economy', 'pitch', …)`), `gig.take` (paid from the business's till with `transferUpTo`, tax to `ext.tax`, energy, 4 gigs/month shared with the old agency `player.gig`, background skill match ×1.5) and `venue.buy` (personal → business; with `withId` a meeting: both spend 2h, the inviter pays for two, contact warmth rises — AI angels and fund partners as `fund` contacts, so warm intros work — and players gain trust both ways). `event.host` takes an optional hospitality `businessId` whose account gets the venue fee. Views: `market.businesses`, `market.economy`, `companies[].businessCustomers`.

Wave 5 (section A): **life, money and work.** Spending costs money only: meals and meetings over a meal (`venue.buy`), event tickets (`event.rsvp`), flights (`travel.fly`, `FLIGHT_HOURS = 0`), rides, furniture and cars; hours stay for company work, hosting, jobs and gigs. New human players start with twice the savings (`HUMAN_SAVINGS_MULTIPLIER`); `player.create` takes an optional `gender` (`view.me.gender`, null for older saves). Jobs (`economy.ts`): every business kind has `roles` (pay in COL units, ×1.25 for a background match); `job.take` (home city, one at a time, 40 hours now and at the start of every month) and `job.quit`; `payJob` in `settlePerson` pays the wage from the till with `transferUpTo`, taxed at home, and ends the job if the business closed. Gigs: 8 a month (shared), and a broke player (`isBroke`: under 2% of a month's living costs, no dollars) can always take the agency gig. `shop.ts` with `data/lifestyle-shop.ts`: `home.buy` (nine slots × three tiers, price to an open furniture store or the suppliers, replacing sells the old one back at 40% from `ext.suppliers`), `car.buy` / `car.sell` (50% back), car running costs at settlement, `city.ride { mode: 'drive' }` free at home with a car, comfort (0–100, up to +8 energy a month) and a status score. Ten new business kinds (nightclub, rooftop lounge, coffee chain, cinema, class studio, car dealership, furniture store, co-working, art gallery, live music) join every roster, and Freetown has a full roster with real streets (`BusinessSeed.street`, `businesses[].street`). Saved worlds need no schema step: new Player fields are optional and `ensureRoster` (own RNG label `'roster'`) opens new roster places at the next settlement while existing ids stay. Views: `market/here.jobs`, `market/here.shop`, `me.job`, `me.home`, `me.car`, `me.status`.
Wave 5 (section B): **capital programmes** in `programs.ts` with `data/programs.ts` (fictional accelerators, development partners and LPs per market; 1–3 accelerators and 2–5 LPs by depth; development partners generous in Freetown, Kigali, Lagos, Nairobi and Accra, scarce in London, SF and Dubai). `accelerator.apply`, `grant.apply` and `lp.pitch` file a `world.applications` entry (stable id `app:<kind>:<target>:<applicant>:<month>`, never `newId`) decided at the target market's next settlement by `settlePrograms` (after the angels, own RNG label `'programs'`): accelerators pay cash on a SAFE held by `accel:<id>` (from and back to `ext.lps`), bump stars, assign a mentor (`company.accelerator`) and hold demo day at the cohort boundary (every 3 months: news, a three-month fundraising bonus in `fundScore`, angel interest, often a SAFE card from a local fund); grants pay 60% now and the rest after a three-month report if the condition holds; LP commitments go into the fund and its size. `invest.quick` proposes model terms through `proposeInvestment` (AI founders answer at once). `angelsAt` places AI angels at meeting venues per period (read-only); `pitch.angel` from there is warm (a fund contact first, optional coffee for two). `event.broadcast` (money only) raises `expectedFill`; events list `attendeesAi` (RSVPs accrue over the month; held events keep `outcome.aiNames`). Each quarter `appointGovernor` names the best licensed human banker governor (`m.governor`; inbox + news). AI startups (`aiStartupTarget`) and angels (`angelTarget(market, humanInvestors)`) shrink as humans join, with minimums of 4 and 2. Views: `market`/`here` carry `accelerators`, `devPartners`, `lps`, `dealFlow`, `angelsAt`, `angels`, `centralBank`; funds and `me` carry an investor type.

Balancing constants live in one place per system (`CUSTOMER_TUNING`, `STAR_TUNING`, salary bands, `OUTLET_EFFECT`), and `npm run sim` prints an economy report to tune them — the design doc lists star values and hours as beta-tuning questions.

## Server (`apps/server`)

- **Single writer.** `GameService` holds the world in memory. Node runs one command at a time and dispatch is synchronous, so commands are serialised without locks.
- **Durability.** The command is appended to SQLite *before* the new world replaces the old one. Snapshots (gzip JSON) every N commands and after each settlement; boot = latest snapshot + replay. A replay that diverges fails loudly rather than serving a wrong world.
- **The clock.** One game month is `MONTH_MINUTES` real minutes (default 30). Time is cut into periods from `CLOCK_EPOCH` (2026-01-01 UTC): period *n* starts at `CLOCK_EPOCH + n × monthMs`. Every 15 s (the long-running server) or every minute (the Netlify scheduled function) the server asks `dueSettlements(world, now, monthMs)` and issues `market.settle { market, at, monthMs }` for each period boundary passed since `MarketState.settledAt` (at most seven per market; an older backlog is skipped). The engine refuses an `at` that isn't later than `settledAt`, so two clock runs racing on the key-value store can't settle a period twice. Saved worlds from the old day clock have no `settledAt`: they settle once at the next boundary and follow periods from then on (no schema step). `market.settle` still accepts the old `{ date }` form so saved command logs replay exactly, and with neither `at` nor `date` it is an extra month (the dev "Advance one month" button) that leaves the clock's schedule alone. `monthMs` on the command drives the rules counted in months of absence (away mode at 2 months auto-hibernates a player's companies with an inbox note, a warning at 6, for sale at 12); without it the old real-day rules apply. `playerView(world, id, { now, monthMs })` adds `view.clock` for the client's countdown. Authenticated requests record the player as seen with a `player.seen` command at most every fifth of a month; it doesn't wake server-sent-event listeners.
- **Being somewhere (Wave 4).** `Player.location` (absent = home) is set by `travel.fly` (one-way fare = half `tripCostUsd`, paid in the home currency to home suppliers, 4 hours, at most six flights a month; flying home is always allowed, standby for whatever cash is left). `view.here` is the location's market in the same shape as `view.market` (which stays the home market for company dashboards); `view.flights.fareTo` prices every other open market from where the player is. Venue buys, gigs, business pitches and event RSVPs check `locationOf(player)`; paying abroad converts from the personal account (`payExact`), and gig pay abroad is converted home and taxed at home. `isVisiting` (in-person fund pitches, fund listings) includes the location. `city.ride` charges a bus (0.2/0.35/0.5% of the local monthly cost of living) or taxi (1/2/3.5%) fare to the location's suppliers, at most 30 a month. Presence is stored and listed by location, so visitors appear on the map of the city they're in. The money-conservation property test covers flights, rides and spending abroad.
- **Feeds.** FX from a free public endpoint every 6 h, with sanity bounds; failures keep the last values.
- **Accounts.** Players start as guests (an 18+ confirmation, no personal data; `users.guest = 1`, `phone_hash = 'guest:<id>'`) and save their progress by confirming an email with a sign-in link (`auth.ts`, `adapters/email.ts`). Link tokens are 256-bit random, single use, 15 minutes, bound to email + intent (+ the asking account for `save`), stored as SHA-256 (`email_tokens` table; `email-token/<hash>` in the key-value store, used with compare-and-swap so two clicks can't both win). One account per email: a unique index in SQLite, and an `email/<sha256(email)>` key claimed create-only in the key-value store (deleted with the account). Asking for a link answers the same whether or not the email has an account. `/api/state` carries `account: { guest, email }`. Phone sign-in endpoints remain for older clients.
- **Security.** Phone numbers stored only as HMAC; OTPs, sign-in link tokens and session tokens stored as SHA-256; OTP attempts limited; links rate-limited per address and per email; production links only ever use `PUBLIC_URL`; `httpOnly` + `SameSite=Strict` cookies plus a required `x-runway` header against CSRF; rate limits; strict CSP; Zod validation at every boundary; logs redact phone, code, email, link tokens and cookies; system commands cannot be sent by clients.
- **Chat** lives outside the simulation (it must never affect outcomes or be visible to reporters/arbitrators): starters only to begin, filters for links/phones/emails/handles, scam flagging, block and report.
- **Presence** (where avatars stand on the city map) also lives outside the simulation, in the account store (`presence` and `presence_settings` tables in SQLite; `presence/<market>/<user>` documents in the key-value store, stale ones pruned on read). Clients report `{ x, y, place }` (rate-limited per player), stored under the city the player is in (`locationOf`), and poll `GET /api/presence`, which returns players in the same city as the viewer (residents and visitors) seen in the last 120 s, minus anyone blocked either way and anyone who has turned "Show me on the map" off (`PUT /api/me/presence`). Positions never reach the engine, reporters or arbitrators, and deleting an account removes them.

### Serverless hosting (Netlify)

The same Fastify app runs inside a Netlify Function: each request is passed through `app.inject`, so routes, validation, security headers and rate limits are identical. Because no process lives long enough to hold the world, `KvGame` keeps it in Netlify Blobs as an event log plus a snapshot. Writing `log/<version>` with "only if new" is the commit point: exactly one writer can produce each version, and a writer that loses the race reloads and re-runs the command on the newer world. Snapshots are written once per version every ten commands and after each settlement (the newest three are kept); a cold function loads the newest and replays the log after it (the engine is deterministic). A warm function only checks whether the next log entry exists. The function code is bundled into one plain JavaScript file at build time (`scripts/build-functions.mjs`), because Netlify copies dependencies as they are and the engine is a TypeScript workspace package. Accounts and chats use per-record compare-and-swap (`KvAccountStore`). The clock is a scheduled function that runs every minute; clients poll instead of holding a server-sent-events connection.

### Scaling path

Markets are independent except for FX and cross-market rules, so the natural next step is one writer per market (shard the command log by market) behind the same API. The read model can be cached per `(player, worldVersion)`. Postgres can replace SQLite behind the `Store` class.

## Web (`apps/web`)

React with hand-written CSS (about 90 KB gzipped, mostly React). Server-sent events tell clients to refetch when the world changes; **lite mode** drops charts and the live connection and polls every minute. A service worker caches the app shell and the public daily digest for offline reading; private state is never cached. Light/dark themes, safe-area insets, reduced-motion support, labelled controls.

**Languages.** English and French (`src/i18n`). Strings are written in English and wrapped in `t('…')`, gettext style, so a missing translation falls back to readable English; placeholders (`{name}`) keep word order free. A test extracts every `t()` call from the source and fails on any string without French or with mismatched placeholders. Server text goes through `tx()`, which translates exact matches. The language is detected from the browser and can be switched on the sign-in screen or in Settings.
